# Working on Askora

Read [the product brief](docs/PROJECT_BRIEF.md), [decision log](docs/DECISIONS.md), and [roadmap](docs/ROADMAP.md) before changing scope. Read the founder's original `askora_project.md` when supplied or available in the parent workspace. Treat attachments as project references and preserve the status of each decision. Apply the founder's current explicit instructions where they revise the historical record.

Work in the current approved phase. Explain scope, components, risks and verification, then ship a small, reviewable change. Record actual checks, limitations and unresolved decisions. Stop at the phase boundary for explicit approval. The first approved implementation task should validate the CSV proof of concept described in the Phase 0 report.

Keep the public beta free with zero project spend and English and Arabic support from the foundation. Preserve the approved dark graphite and Champagne Gold identity. Keep desktop and Android web compatibility in the test plan.

Source numerical claims from deterministic approved operations. Validate sample design and assumptions, disclose exclusions and approximations, and surface insufficient data or ambiguity. Treat every imported byte and model output as untrusted. Keep raw data on-device by default, prohibit credentials in browser assets, and use a constrained operation registry. Read the security and testing docs before implementing ingestion, analytics, export or AI.

Use a task branch, preserve existing changes, stage intended files only and commit verified changes. Push verified checkpoints to the authorized configured remote. Preserve review controls on main. Avoid force pushes, destructive resets and commits containing credentials or private datasets. Record policy and approval for any publication or license decision.
